# Architecture

The structure optimizes for three things: a new feature never has to touch
unrelated code, rules are testable without a device, and the build tells you
when the structure is broken.

## Layout

```
lib/
  main.dart                 starts the app with production dependencies
  app/                      composition root: wiring and navigation between features
  core/                     shared building blocks, no feature knowledge
    config/                 build info, Firebase options
    design_system/          theme, fonts, reusable widgets
  features/<feature>/
    domain/                 pure Dart: models, rules, repository interfaces
    application/            state and use cases (ChangeNotifier controllers)
    data/                   adapters to the outside world (Firebase, platform APIs)
    presentation/           widgets and screens
  l10n/                     ARB files and the generated localizations
```

Example features: `auth` (sign-in, linking, sign-out) and `home` (the screen
after signing in).

## Dependency rules

| Layer | May import |
|---|---|
| domain | domain (any feature), core. No Flutter or third-party packages, no `dart:io`/`dart:ui` |
| application | domain, application (any feature), core |
| data | domain, data (own feature), core, third-party SDKs |
| presentation | own feature's domain/application/presentation, other features' domain/application, core, l10n |
| core | core only |
| app | anything (it is the only place that knows concrete implementations) |

Features never import each other's `presentation` or `data`. When one screen
shows another feature's widget, `lib/app` passes it in: `HomeScreen` takes an
`accountPanel`, and `app/app.dart` hands it the auth feature's
`LinkAccountCard`. `test/architecture_test.dart` enforces these rules, so
breaking them fails CI.

## Dependency injection

`app/app_dependencies.dart` builds everything once
(`AppDependencies.production()`). Tests build their own `AppDependencies` with
fakes from `test/support/`. No service locator, no globals: dependencies go
in through constructors.

External things hide behind small interfaces in `domain`. `AuthGateway` has
three implementations: `FirebaseAuthGateway` (the real one),
`DemoAuthGateway` (builds without Firebase config: simulated sign-in on the
device) and `FakeAuthGateway` in tests.

## State

Plain Flutter: `ChangeNotifier` controllers in `application/`, rebuilt with
`ListenableBuilder`. If state sharing grows beyond constructor passing,
revisit with an ADR (Riverpod is the likely candidate).

## Sign-in

- **Google**: `google_sign_in` gets an ID token, Firebase signs in with it.
  Android asks for a token for the project's web OAuth client
  (`GOOGLE_SERVER_CLIENT_ID`), iOS uses its own client (`GOOGLE_IOS_CLIENT_ID`)
  and returns to the app through the reversed client ID URL scheme.
- **Apple**: Firebase's native `AppleAuthProvider`, iPhone and iPad only.
- **Without an account**: an anonymous Firebase user.
- **Linking**: an anonymous user links Google or Apple with
  `linkWithCredential`/`linkWithProvider` and keeps the same uid, so
  everything saved under it stays. When the account already belongs to
  another user (`credential-already-in-use`), the home screen asks whether to
  switch to that user.

Firebase options come from the files in `firebase/` at build time
(`--dart-define-from-file`, see `firebase/README.md`), so the repository holds
no project config.

## Localization

`lib/l10n/app_en.arb` is the template; every other language has the same keys
and placeholders. Every English message has an `@key` entry with a
`description` saying where the text appears and what its placeholders are, so
translators never guess. `test/l10n/translations_test.dart` enforces both.
Texts are generated by `flutter gen-l10n` (on `pub get` and in
`scripts/check.sh`) into `lib/l10n/gen/`, which is not committed. Widgets read
them with `context.l10n`.

## Screenshots and the catalog

`widgetbook/stories.dart` (components) and `widgetbook/screens.dart` (whole
screens) are the single source for both the Widgetbook catalog and the golden
screenshot tests in `test/screenshots/`. Screens render on every device in
`widgetbook/devices.dart` (phones and a tablet) in every language; a layout
overflow fails the test. The PNGs are for looking at (CI artifact), not
committed baselines.
